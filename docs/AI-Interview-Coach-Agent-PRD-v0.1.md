# AI Interview Coach Agent PRD v0.1

## 1. 项目概述

### 1.1 项目名称

AI Interview Coach Agent：面向求职者的简历岗位匹配与模拟面试助手。

### 1.2 项目定位

本项目不是一个泛聊天机器人，而是一个围绕求职准备流程工作的 Agent 系统。它帮助用户从“看到一个岗位”开始，完成简历匹配分析、笔试面试准备、模拟面试、面试复盘和后续提升计划。

核心目标：

1. 帮用户理解自己的简历与目标岗位 JD 的差距。
2. 基于简历、JD、面经生成有针对性的面试题。
3. 对用户的面试回答或面试录音进行分析复盘。
4. 将每次练习和复盘结果沉淀为个人求职记忆，持续优化后续训练内容。

### 1.3 目标用户

第一阶段目标用户：

1. 在校大学生：准备实习、校招、考研复试、项目面试。
2. 社会求职者：准备转岗、跳槽、复盘真实面试表现。

用户共同特点：

1. 有简历，但不确定简历是否匹配目标岗位。
2. 找到岗位 JD 后，不知道应该重点准备哪些知识点和项目问题。
3. 面试练习缺少结构化反馈。
4. 面试结束后不知道如何复盘，容易只凭感觉判断表现。

## 2. 业务背景与问题

### 2.1 用户真实场景

用户在求职过程中通常会经历以下流程：

1. 浏览招聘平台，找到一个感兴趣的岗位。
2. 阅读 JD，但难以判断自己是否匹配。
3. 修改简历，但不知道应该突出哪些经历。
4. 搜索相关面经，但信息分散且质量不稳定。
5. 准备笔试和面试，但练习不够针对目标岗位。
6. 参加真实面试后，无法系统复盘自己的回答表现。

### 2.2 当前痛点

1. 简历和 JD 的匹配判断依赖主观感觉，缺少结构化分析。
2. 面试题准备容易泛化，不能围绕用户自己的项目和目标岗位展开。
3. 面经信息很多，但用户不知道如何筛选、归纳和转化为训练题。
4. 模拟面试没有评分标准，用户不知道自己回答好在哪里、差在哪里。
5. 真实面试录音或回忆没有被沉淀，下一次准备无法复用历史经验。

## 3. MVP 业务闭环

### 3.1 MVP 目标

第一版先做一个完整闭环：

用户输入简历和岗位 JD，系统输出岗位匹配分析、简历优化建议、模拟面试题；用户回答后，系统给出评分、改进建议和下一步准备计划。

### 3.2 MVP 流程

```text
用户上传或粘贴简历
↓
用户粘贴目标岗位 JD
↓
可选：用户粘贴面经或上传面试录音转写文本
↓
系统解析简历、JD、面经
↓
系统生成简历-JD 匹配分析
↓
系统生成针对性面试题
↓
用户回答面试题
↓
系统按照评分标准评价回答
↓
系统给出改进建议、参考回答和复习计划
↓
系统将薄弱点写入用户记忆，用于下一轮训练
```

### 3.3 MVP 输入

必需输入：

1. 用户简历：文本、PDF 或 DOCX，第一版可以先支持文本。
2. 目标岗位 JD：用户从招聘网站复制的岗位描述。

可选输入：

1. 面经：来自网上相似岗位的面经，或用户自己历史面试记录。
2. 面试录音：第一版可以先不直接处理音频，先支持录音转写后的文本。

### 3.4 MVP 输出

1. 简历与 JD 的匹配度分析。
2. 用户当前优势。
3. 用户当前短板。
4. 简历修改建议。
5. 可能被重点追问的项目经历。
6. 针对目标岗位的模拟面试题。
7. 用户回答评分。
8. 回答中表现好的地方。
9. 回答中需要改进的地方。
10. 改进版回答示例。
11. 下一步复习计划。

## 4. 核心功能需求

### 4.1 简历解析

系统需要从用户简历中提取：

1. 基本信息。
2. 教育背景。
3. 技术技能。
4. 项目经历。
5. 实习或工作经历。
6. 奖项、证书、论文、竞赛等补充信息。

结构化输出示例：

```json
{
  "skills": ["Python", "FastAPI", "React", "MySQL"],
  "projects": [
    {
      "name": "校园课程智能助手",
      "role": "后端开发",
      "tech_stack": ["FastAPI", "RAG", "MySQL"],
      "highlights": ["实现课程问答", "接入知识库检索"]
    }
  ]
}
```

### 4.2 JD 解析

系统需要从岗位 JD 中提取：

1. 岗位名称。
2. 岗位职责。
3. 硬性要求。
4. 加分项。
5. 技术关键词。
6. 隐含能力要求，例如沟通、协作、工程规范、业务理解。

### 4.3 简历-JD 匹配分析

系统需要基于简历和 JD 生成：

1. 总体匹配度。
2. 技术栈匹配情况。
3. 项目经历匹配情况。
4. 学历、经验、业务背景匹配情况。
5. 缺失能力或表达不足。
6. 可直接修改的简历建议。

匹配分析必须带依据，避免空泛评价。

示例：

```text
JD 强调 FastAPI 和数据库设计。你的简历中出现 FastAPI 和 MySQL，但项目描述更偏功能介绍，没有体现接口设计、权限控制、数据库建模和性能优化，因此建议补充这些工程细节。
```

### 4.4 面经处理

面经不是必需输入，但系统需要支持将面经作为增强材料。

面经来源：

1. 用户自己历史面试记录。
2. 用户从网上复制的相似岗位面经。
3. 用户手动整理的笔试题或面试题。

系统需要从面经中提取：

1. 高频知识点。
2. 高频问题。
3. 面试官追问方向。
4. 与目标 JD 相关的部分。
5. 与用户简历项目相关的部分。

### 4.5 模拟面试题生成

系统需要生成多类面试题：

1. 简历项目追问题。
2. JD 技术要求问题。
3. 基础知识问题。
4. 场景设计题。
5. 行为面试题。
6. 面经相似题。

每道题需要包含：

1. 问题正文。
2. 考察点。
3. 难度。
4. 来源依据：来自简历、JD、面经或综合推断。
5. 参考答题要点。

### 4.6 回答评分

用户回答一道题后，系统需要按照评分标准给出反馈。

评分维度：

1. 相关性：是否回答了问题。
2. 准确性：技术点是否正确。
3. 结构性：是否有清晰逻辑。
4. 具体性：是否结合项目细节。
5. 表达力：是否简洁、有重点。
6. 风险点：是否暴露明显知识漏洞或夸大经历。

评分输出：

```text
总分：78 / 100

表现好的地方：
1. 能够说明项目背景和个人职责。
2. 提到了 FastAPI 和数据库表设计。

需要改进的地方：
1. 缺少具体技术决策理由。
2. 没有说明遇到的问题和解决方案。
3. 对性能优化描述比较空泛。

改进建议：
使用 STAR 结构重写回答，补充项目中的真实难点、你的行动和结果。
```

### 4.7 面试复盘

当用户输入真实面试录音转写文本或面试回忆时，系统需要输出复盘报告。

复盘内容：

1. 面试问题列表。
2. 用户回答表现。
3. 表现好的问题。
4. 表现不佳的问题。
5. 高频薄弱知识点。
6. 下一次面试前需要补强的内容。
7. 简历中可能引发追问但准备不足的部分。

### 4.8 复习计划生成

系统需要根据匹配分析、模拟面试评分和真实面试复盘生成复习计划。

计划内容：

1. 优先级最高的 3 到 5 个薄弱点。
2. 每个薄弱点对应的复习任务。
3. 推荐练习题。
4. 下一轮模拟面试题。
5. 预计完成时间。

## 5. Agent 系统设计要求

### 5.1 Harness 层

Harness 层负责管理整个 Agent 系统运行，而不是让一个大模型一次性完成所有事情。

Harness 需要负责：

1. Agent 调度：决定当前任务应该交给哪个 Agent。
2. 状态管理：保存当前用户、目标岗位、简历解析结果、历史训练结果。
3. 记忆管理：区分短期会话记忆和长期用户记忆。
4. 工具调用：管理文件解析、检索、转写、评分、报告生成等工具。
5. 结果校验：检查 Agent 输出是否符合结构化格式。
6. 失败重试：当某个 Agent 输出不合格时触发重试或降级策略。
7. 审计日志：记录每一步 Agent 输入、输出、工具调用和最终结果。

### 5.2 多 Agent 分工

第一版可以设计为以下 Agent：

1. Resume Analyzer Agent：负责简历解析和简历亮点提取。
2. JD Analyzer Agent：负责岗位要求解析。
3. Matching Agent：负责简历与 JD 匹配分析。
4. Interview Question Agent：负责生成模拟面试题。
5. Interview Evaluator Agent：负责回答评分和反馈。
6. Coach Agent：负责改写回答、生成复习计划。
7. Memory Agent：负责沉淀用户薄弱点和历史训练记录。

### 5.3 Agent 通信方式

Agent 之间不直接传递自由文本，而是尽量传递结构化结果。

示例：

```text
Resume Analyzer Agent
  -> ResumeProfile

JD Analyzer Agent
  -> JDProfile

Matching Agent
  <- ResumeProfile + JDProfile
  -> MatchReport

Interview Question Agent
  <- ResumeProfile + JDProfile + Optional InterviewExperienceSummary
  -> QuestionSet

Interview Evaluator Agent
  <- Question + UserAnswer + Rubric
  -> AnswerEvaluation

Coach Agent
  <- AnswerEvaluation + UserMemory
  -> ImprovedAnswer + StudyPlan
```

### 5.4 记忆设计

系统记忆分为三类：

1. 会话记忆：当前一次分析或模拟面试中的上下文。
2. 用户长期记忆：用户常见薄弱点、常投岗位、常见项目、表达习惯。
3. 资料记忆：简历版本、历史 JD、历史面经、历史面试复盘。

长期记忆示例：

```json
{
  "weaknesses": ["数据库索引解释不清", "项目难点描述不具体"],
  "strong_areas": ["项目背景表达清楚", "能说明个人职责"],
  "target_roles": ["后端开发实习", "AI 应用开发"],
  "last_training_focus": ["FastAPI 权限设计", "RAG 检索流程"]
}
```

## 6. 评测机制

### 6.1 为什么需要评测

Agent 项目的难点不只是“能生成内容”，而是要证明生成结果可靠、有用、可改进。

本项目需要从两个角度评测：

1. Agent 输出质量：系统生成的分析、问题、反馈是否靠谱。
2. 用户使用价值：用户是否真的能通过系统提升求职准备质量。

### 6.2 可量化指标

第一版可以采用以下指标：

1. 简历信息提取准确率：抽取出的技能、项目、经历是否正确。
2. JD 要求提取准确率：岗位职责、硬性要求、加分项是否正确。
3. 匹配分析证据覆盖率：每条分析是否能追溯到简历或 JD。
4. 面试题相关性评分：题目是否与简历、JD、面经相关。
5. 反馈可执行性评分：改进建议是否具体到可以修改回答或复习。
6. 回答评分一致性：同一回答多次评分是否稳定。
7. 用户采纳率：用户是否采用了简历建议或改写回答。
8. 训练后提升幅度：同类问题多轮练习后的得分是否提升。

### 6.3 人工评测 Rubric

对于每份报告，可以人工按 1 到 5 分评价：

| 维度 | 1 分 | 3 分 | 5 分 |
| --- | --- | --- | --- |
| 相关性 | 泛泛而谈 | 部分结合 JD 或简历 | 明确结合简历和 JD |
| 证据性 | 无依据 | 有少量依据 | 每个结论有来源 |
| 可执行性 | 不知道怎么改 | 有方向但不具体 | 能直接修改简历或回答 |
| 准确性 | 有明显错误 | 基本正确 | 技术判断可靠 |
| 个性化 | 像通用模板 | 部分个性化 | 明显基于用户材料 |

### 6.4 自动评测思路

可以设计一批测试样例：

1. 简历样例。
2. JD 样例。
3. 标准抽取结果。
4. 标准评分点。
5. 用户回答样例。

然后让系统输出结果，与标准答案或人工标注结果对比。

自动评测可以包含：

1. JSON Schema 校验：输出结构是否正确。
2. 关键词召回率：是否提取到关键技能和要求。
3. 证据引用检查：分析结论是否引用了输入材料。
4. 自一致性检查：多次运行结果是否过度波动。
5. LLM-as-judge：用单独的评测模型根据 Rubric 给分。

## 7. 自进化机制

### 7.1 自进化定义

本项目中的自进化不是让 Agent 自动改代码，也不是让模型自己训练自己，而是让系统根据用户反馈和历史表现优化后续策略。

### 7.2 可实现方式

1. 用户反馈：用户对报告、问题、评分进行点赞、点踩或文字反馈。
2. 策略调整：根据反馈调整后续题目生成方向和评分重点。
3. 长期记忆更新：将反复出现的薄弱点写入用户画像。
4. 面试题推荐优化：优先生成用户历史上表现差、目标岗位要求高的问题。
5. Prompt 版本管理：记录不同提示词版本的效果，用评测集对比。
6. Rubric 迭代：根据人工评测结果优化评分标准。

### 7.3 自进化闭环

```text
生成结果
↓
用户使用或反馈
↓
系统记录采纳、修改、评分变化
↓
更新用户记忆和策略参数
↓
下一次生成更有针对性的题目和建议
↓
通过评测指标验证是否变好
```

## 8. 如何判断输出有用

你当前还不确定“如何判断输出有用”，这是正常的。第一版可以先把“有用”拆成四类指标。

### 8.1 对简历分析是否有用

可观察信号：

1. 用户能根据建议直接修改简历。
2. 建议不是泛泛而谈，而是指出具体项目、具体描述、具体缺失点。
3. 每条建议都能对应 JD 中的某个要求。
4. 用户修改后，简历与 JD 的匹配得分提升。

### 8.2 对面试准备是否有用

可观察信号：

1. 生成的问题确实可能被面试官追问。
2. 问题覆盖 JD 技术点、用户项目、面经高频点。
3. 用户练习后能知道自己哪类问题最弱。
4. 下一轮练习不是随机出题，而是围绕薄弱点强化。

### 8.3 对面试复盘是否有用

可观察信号：

1. 系统能指出回答中具体哪句话不清楚或有风险。
2. 系统能总结出用户的重复问题，例如表达空泛、缺少数据、技术细节不足。
3. 系统能把复盘结果转化为下一次练习任务。

### 8.4 对求职结果是否有用

长期指标：

1. 用户投递前准备时间是否减少。
2. 用户模拟面试得分是否提升。
3. 用户真实面试复盘中的薄弱点是否减少。
4. 用户是否更愿意持续使用系统准备不同岗位。

## 9. 第一版不做的内容

为了避免项目失控，第一版暂不做：

1. 登录注册。
2. 支付。
3. 自动投递。
4. 招聘网站爬虫。
5. 自动搜索全网面经。
6. 语音实时面试。
7. 多人协作。
8. 企业 HR 端。

## 11. 当前待确认问题

下一轮需要重点确认：

1. 第一版优先服务哪类岗位：后端开发、前端开发、AI 应用开发、数据分析，还是通用技术岗？
2. 简历输入第一版是否只支持文本，还是一开始就支持 PDF / DOCX？
3. 面试录音第一版是否先只支持转写文本？
4. 面经来源是否由用户手动粘贴，而不是系统自动搜索？
5. 模拟面试第一版做单题评分，还是做完整一轮面试？
6. 是否需要把“笔试准备”纳入第一版，还是先专注面试？
